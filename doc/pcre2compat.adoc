== Differences between PCRE2 and Perl

This document describes some of the known differences in the ways that PCRE2
and Perl handle regular expressions. The differences described here are with
respect to Perl version 5.44.0, with changes in the development release 5.45.4
noted explicitly. As both Perl and PCRE2 are continually changing, the information
may at times be out of date.

* When const:PCRE2_DOTALL (equivalent to Perl's [.regex]`/s` qualifier) is not set, the
behaviour of the [.regex]`.` metacharacter differs from Perl. In PCRE2, [.regex]`.` matches the
next character unless it is the start of a newline sequence. This means that,
if the newline setting is CR, CRLF, or NUL, [.regex]`.` will match the code point LF
(char:0x0A) in ASCII/Unicode environments, and NL (either char:0x15 or char:0x25) when using
EBCDIC. In Perl, [.regex]`.` appears never to match LF, even when char:0x0A is not a newline
indicator.

* PCRE2 has only a subset of Perl's Unicode support. Details of what it does
have are given in the
xref:pcre2unicode.adoc[`pcre2unicode`]
page.

* Like Perl, PCRE2 allows repeat quantifiers on parenthesized assertions, but
they do not mean what you might think. For example, [.regex]`+(?!a){3}+` does not assert
that the next three characters are not [.subject]`a`. It just asserts that the next
character is not [.subject]`a` three times (in principle; PCRE2 optimizes this to run the
assertion just once). Perl allows some repeat quantifiers on other assertions,
for example, [.regex]`+\b*+` , but these do not seem to have any use. PCRE2 does not allow
any kind of quantifier on non-lookaround assertions.

* If a braced quantifier such as [.regex]`+{1,2}+` appears where there is nothing to
repeat (for example, at the start of a branch), PCRE2 raises an error whereas
Perl treats the quantifier characters as literal. When a braced quantifier
[.regex]`(\...){_min_,_max_}` has _min_ > _max_, Perl treats it as an item which fails to match
any portion of the subject (as no number of repetitions can meet the
condition), and additionally issues a warning when in warning mode. PCRE2 has
no warning features, so it gives an error in this case.

* Capture groups that occur inside negative lookaround assertions are counted,
but their entries in the offsets vector are set only when a negative assertion
is a condition that has a matching branch (that is, the condition is false).
Earlier versions of Perl could also leave captures set after unsuccessful
assertion attempts in other circumstances. Perl 5.45.4 restores captures after
evaluating negative assertions, including those used as conditions. PCRE2
retains its previous behaviour for a false negative assertion condition.

* Both Perl and PCRE2 support variable-length lookbehind, but they can choose
different captures. With the subject [.subject]`aaz`, the pattern
[.regex]`+(?=z)(?<=(a)|(aa))+` sets group 1 to [.subject]`a` in PCRE2, whereas
Perl 5.36.0 and later set group 2 to [.subject]`aa`. PCRE2 tries the lookbehind's top-level
alternatives in order; Perl tries the longest available lookbehind first.
However, [.regex]`+(?=z)(?<=(a|aa))+`, with the alternatives inside one
capturing group, captures [.subject]`aa` in both engines.

* The following Perl escape sequences are not supported: [.regex]`\F`, [.regex]`\l`, [.regex]`\L`, [.regex]`\u`,
[.regex]`\U`, and [.regex]`\N` when followed by a character name. [.regex]`\N` on its own, matching a
non-newline character, and [.regex]`\N{U+__dd\...__}`, matching a Unicode code point, are
supported; the numeric [.regex]`\N{U+__dd\...__}` form requires UTF mode.
The escapes that modify the case of following letters are
implemented by Perl's general string-handling and are not part of its pattern
matching engine. If any of these are encountered by PCRE2, an error is
generated by default. However, if either of the const:PCRE2_ALT_BSUX or
const:PCRE2_EXTRA_ALT_BSUX options is set, [.regex]`\U` and [.regex]`\u` are interpreted as ECMAScript
interprets them.

* Perl removed [.regex]`\C` in release 5.24.0. PCRE2 retains it for matching a
single code unit, including part of a UTF character. Its use can be disabled,
and there are restrictions on its use with UTF, DFA matching, and JIT. See
xref:pcre2pattern.adoc[`pcre2pattern`]
for details.

* The Perl escape sequences [.regex]`\p`, [.regex]`\P`, and [.regex]`\X` are supported only if PCRE2 is
built with Unicode support (the default). The properties that can be tested
with [.regex]`\p` and [.regex]`\P` are limited to the general category properties such as
[.regex]`Lu` and [.regex]`Nd`, the derived properties [.regex]`Any` and [.regex]`Lc`
(synonym [.regex]`L&`), script names such as [.regex]`Greek` or [.regex]`Han`,
[.regex]`Bidi_Class`, [.regex]`Bidi_Control`, and a few binary properties. Both PCRE2 and
Perl support the [.regex]`Cs` (surrogate) property, but in PCRE2 its use is limited. See
the
xref:pcre2pattern.adoc[`pcre2pattern`]
documentation for details. The long synonyms for property names that Perl
supports (such as [.regex]`+\p{Letter}+`) are not supported by PCRE2, nor is it permitted
to prefix any of these properties with [.regex]`Is`.

* PCRE2 supports the [.regex]`+\Q...\E+` escape for quoting substrings. Characters
in between are treated as literals. However, this is slightly different from
Perl in that [.regex]`$` and [.regex]`@` are also handled as literals inside the quotes. In Perl,
they cause variable interpolation (PCRE2 does not have variables). Also, Perl
does "double-quotish backslash interpolation" on any backslashes between [.regex]`\Q`
and [.regex]`\E` which, its documentation says, "may lead to confusing results". PCRE2
treats a backslash between [.regex]`\Q` and [.regex]`\E` just like any other character. Note the
following examples:

+
[cols="1,1,2",options="header"]
|===
|Pattern                       | PCRE2 matches          | Perl matches
|[.regex]`+\Qabc$xyz\E+`       | [.subject]`abc$xyz`    | [.subject]`abc` followed by the contents of `$xyz`
|[.regex]`+\Qabc\$xyz\E+`      | [.subject]`abc\$xyz`   | [.subject]`abc\$xyz`
|[.regex]`+\Qabc\E\$\Qxyz\E+`  | [.subject]`abc$xyz`    | [.subject]`abc$xyz`
|[.regex]`+\QA\B\E+`           | [.subject]`A\B`        | [.subject]`A\B`
|[.regex]`+\Q\\E+`             | [.subject]`\`          | [.subject]`\\E`
|===

+
The [.regex]`+\Q...\E+` sequence is recognized both inside and outside character classes
by both PCRE2 and Perl. Another difference from Perl is that any appearance of
[.regex]`\Q` or [.regex]`\E` inside what might otherwise be a quantifier causes PCRE2 not to
recognize the sequence as a quantifier. Perl recognizes a quantifier if
(redundantly) either of the numbers is inside [.regex]`+\Q...\E+`, but not if the
separating comma is. When not recognized as a quantifier a sequence such as
[.regex]`+{\Q1\E,2}+` is treated as the literal string [.subject]`{1,2}`.

* Fairly obviously, PCRE2 does not support the [.regex]`(?{__code__})` and
[.regex]`(??{__code__})`
constructions. However, PCRE2 does have a "callout" feature, which allows an
external function to be called during pattern matching. See the
xref:pcre2callout.adoc[`pcre2callout`]
documentation for details.

* Subroutine calls (whether recursive or not) were treated as atomic groups
up to PCRE2 release 10.23, but from release 10.30 this changed, and
backtracking into subroutine calls is now supported, as in Perl.

* In PCRE2, [.regex]`+(*COMMIT)+`, [.regex]`+(*SKIP)+`, and [.regex]`+(*PRUNE)+`,
when triggered in a group called as a subroutine (whether or not recursively),
cause the subroutine match to fail, but allow backtracking in the caller.
Their effect does not extend to the surrounding pattern as it can in Perl.
Similarly, if [.regex]`+(*THEN)+` is present in a group
that is called as a subroutine, its action is limited to that group, even if
the group does not contain any [.regex]`|` characters. Note that such groups are
processed as anchored at the point where they are tested.

+
In atomic assertions, PCRE2 confines [.regex]`+(*THEN)+` to the assertion,
including assertions with only one branch. Other verbs are not necessarily
confined in this way. For example, [.regex]`+\A(?:(?=a(*COMMIT)c)ab|ab)\z+`
does not match [.subject]`ab` in either PCRE2 or Perl: [.regex]`+(*COMMIT)+`
is triggered while the standalone positive assertion is being evaluated,
and prevents the outer alternative from being tried. Once an atomic assertion
has succeeded, a later failure outside it cannot backtrack into it to trigger
a verb. See "Backtracking verbs in assertions" in
xref:pcre2pattern.adoc[`pcre2pattern`]
for details.

* If a pattern contains more than one backtracking control verb, the first
one that is backtracked onto acts. For example, in the pattern
[.regex]`A(*COMMIT)B(*PRUNE)C` a failure in [.regex]`B` triggers [.regex]``(*COMMIT)``, but a failure in [.regex]`C`
triggers [.regex]``(*PRUNE)``. Perl's behaviour is more complex; in many cases it is the
same as PCRE2, but there are cases where it differs. For example,
[.regex]`+(A(*COMMIT)B(*THEN)C|ABD)+` matches [.subject]`ABD` in PCRE2,
but not in Perl 5.44.0.

* There are some differences that are concerned with the settings of captured
strings when part of a pattern is repeated. For example, matching [.subject]`aba` against
the pattern [.regex]`^(a(b)?)+$` in Perl leaves [.regex]`$2` unset, but in PCRE2 it is set to
[.subject]`b`. Since Perl 5.38.0, the pattern
[.regex]`((foo)baz|foo(bar))+` matched against [.subject]`foobazfoobar` leaves
group 2 unset in Perl, but set to [.subject]`foo` in PCRE2.

+
These differences can also affect whether a match succeeds. Perl 5.45.4 made
capture clearing consistent when a repeated subpattern matches zero times.
PCRE2 retains a capture from an earlier iteration when a later iteration skips
that capture. For example, [.regex]`+\A(?:(a+)?b)+\1\z+` matches [.subject]`abba`
in PCRE2, but not in Perl 5.45.4.

* PCRE2's handling of duplicate capture group numbers and names is not as
general as Perl's. This is a consequence of the fact the PCRE2 works internally
just with numbers, using an external table to translate between numbers and
names. In particular, a pattern such as [.regex]`+(?|(?<a>A)|(?<b>B))+`, where the two
capture groups have the same number but different names, is not supported, and
causes an error at compile time. If it were allowed, it would not be possible
to distinguish which group matched, because both names map to capture group
number 1. To avoid this confusing situation, an error is given at compile time.

* Capture group names are not validated identically. Perl 5.44.0 tightened
the permitted continuation characters using Unicode's
[.regex]`XID_Continue` property. PCRE2's rules still permit some characters
that Perl rejects, for example char:U+037A (GREEK YPOGEGRAMMENI) after the first
character of a name in UTF mode.

* Older Perl releases allowed white space or comments between the [.regex]`(`
and [.regex]`?` at the start of a group. Perl 5.18.0 deprecated this, and
Perl 5.22.0 made it an error. PCRE2 also rejects these constructs; this is
not a difference from Perl 5.44.0.

* Perl has progressively restricted unescaped literal left braces. For example,
Perl rejects [.regex]`+\s{foo}+` (since 5.26.0), whereas PCRE2 treats
the braces in this pattern as literals. Escaping literal braces avoids these
differences.

* Perl 5.44.0 introduced the experimental, opt-in `enhanced_xx` feature,
which permits comments and ignored vertical whitespace inside ordinary
bracketed classes under [.regex]`/xx`. PCRE2 retains the earlier [.regex]`/xx`
rules: only unescaped space and horizontal tab are ignored inside such classes;
an unescaped [.regex]`#` or a literal newline is a class member, not the start
of a comment or ignored whitespace.

* Perl supports Unicode case folds involving more than one character, such as
matching [.regex]`ss` against char:U+00DF (LATIN SMALL LETTER SHARP S) with
caseless matching. PCRE2 supports only single-character case folds.

* Perl, when in warning mode, gives warnings for character classes such as
[.regex]`+[A-\d]+` or [.regex]`+[a-[:digit:]]+`. It then treats the hyphens as literals. PCRE2 has no
warning features, so it gives an error in these cases because they are almost
certainly user mistakes.

* Before PCRE2 release 10.45, the upper/lower case character properties
[.regex]`Lu` and [.regex]`Ll` were not affected when case-independent matching was specified. Perl has
changed in this respect, and PCRE2 has now changed to match. When caseless
matching is in force, [.regex]`Lu`, [.regex]`Ll`, and [.regex]`Lt` (title case)
are all treated as [.regex]`Lc` (cased letter).

* From release 5.32.0, Perl locks out the use of [.regex]`\K` in lookaround
assertions. From release 10.38 PCRE2 does the same by default. However, there
is an option for re-enabling the previous behaviour. When this option is set,
[.regex]`\K` is acted on when it occurs in positive assertions, but is ignored in
negative assertions.

* PCRE2 provides some extensions to the Perl regular expression facilities.
Perl 5.10 included new features that were not in earlier versions of Perl, some
of which (such as named parentheses) were in PCRE2 for some time before. This
list is with respect to Perl 5.44:

+
[loweralpha]
. If const:PCRE2_DOLLAR_ENDONLY is set and const:PCRE2_MULTILINE is not set, the [.regex]`$`
meta-character matches only at the very end of the string.

. A backslash followed by a letter with no special meaning is faulted. (Perl
can be made to issue a warning.)

. If const:PCRE2_UNGREEDY is set, the greediness of the repetition quantifiers is
inverted, that is, by default they are not greedy, but if followed by a
question mark they are.

. const:PCRE2_ANCHORED can be used at matching time to force a pattern to be tried
only at the specified starting offset in the subject string.

. The const:PCRE2_NOTBOL, const:PCRE2_NOTEOL, const:PCRE2_NOTEMPTY and const:PCRE2_NOTEMPTY_ATSTART
options have no Perl equivalents.

. The [.regex]`\R` escape sequence can be restricted to match only CR,
LF, or CRLF
by the const:PCRE2_BSR_ANYCRLF option.

. The callout facility is PCRE2-specific. Perl supports codeblocks and
variable interpolation, but not general hooks on every match.

. The partial matching facility is PCRE2-specific.

. The alternative matching function (func:pcre2_dfa_match()) matches in a
different way and is not Perl-compatible.

. PCRE2 recognizes some special sequences such as [.regex]`+(*CR)+` or [.regex]`+(*NO_JIT)+` at
the start of a pattern. These set overall options that cannot be changed within
the pattern.

. PCRE2 supports non-atomic positive lookaround assertions. This is an
extension to the lookaround facilities. The default, Perl-compatible
lookarounds are atomic.

. There are three syntactical items in patterns that can refer to a capturing
group by number: back references such as [.regex]`+\g{2}+`, subroutine calls such as [.regex]`+(?3)+`,
and condition references such as [.regex]`+(?(4)...)+`. PCRE2 supports relative group
numbers such as [.regex]`+2` and [.regex]`-4` in all three cases. Perl supports both plus and minus
for subroutine calls, but only minus for back references, and no relative
numbering at all for conditions.

. The scan substring assertion (syntax [.regex]`(*scs:(_n_)\...)`) is a PCRE2 extension
that is not available in Perl.

* Perl has different limits than PCRE2. See the
xref:pcre2limits.adoc[`pcre2limits`]
documentation for details. Perl 5.10 replaced recursive matching with
iteration, keeping intermediate matching states on the heap. PCRE2 made a
similar change at release 10.30, and also has many build-time and run-time
customizable limits. These changes do not eliminate every use of the system
stack, for example during pattern compilation.

* PCRE2 does not implement Perl's character set modes [.regex]`+/d+`,
[.regex]`+/l+`, [.regex]`+/u+`, [.regex]`+/a+`, and [.regex]`+/aa+`, in particular
the context-dependent behaviour of [.regex]`+/d+`. A regular expression using
const:PCRE2_UTF and const:PCRE2_UCP will use similar rules to Perl's [.regex]`+/u+`; something closer
to [.regex]`+/a+` can be selected by adding `+PCRE2_EXTRA_ASCII*+` options.
These restrictions can also be set within a pattern using PCRE2's own
[.regex]`+(?a)+` options, such as [.regex]`+(?aT)+`, [.regex]`+(?aP)+`,
and [.regex]`+(?aD)+`. These are not the same as Perl's character set modes.

* Some recursive patterns that Perl diagnoses as infinite recursions can be
handled by PCRE2, either by the interpreter or the JIT. An example is
[.regex]`+(?:|(?0)abcd)(?(R)|\z)+`, which in PCRE2 matches a sequence of any
number of repeated [.subject]`abcd` substrings at the end of the subject.
Perl 5.44.0 matches [.subject]`abcd`, but raises an infinite-recursion error
for [.subject]`abcdabcd`.

* Both PCRE2 and Perl error when [.regex]`+\x{+` escapes are invalid, but Perl tries to
recover and prints a warning if the problem was that an invalid hexadecimal
digit was found. Since PCRE2 doesn't have warnings it returns an error instead.
Additionally, Perl accepts [.regex]`+\x{}+` and matches NUL unlike PCRE2.

* From release 10.45, PCRE2 gives an error if [.regex]`\x` is not followed by a
hexadecimal digit or a curly bracket. It used to interpret this as the NUL
character. Perl still matches NUL, but warns when in warning mode in most
cases.
